## D. WHY AETHER IS SLOW — ROOT CAUSE: hardware ceiling (confirmed, not a bug)

- Model: `qwen3.8-27b` @ **IQ4_XS**, `NUM_CTX = 8192`, ~15 GB resident, 2× Tesla T4 per engine.
- Decode: **14.5–15.4 tok/s, flat across num_ctx/num_batch** — single-stream decode on T4 is memory-bandwidth-bound (~320 GB/s per card). `PERFORMANCE_CEILING.md` says "do not chase it with settings" and the data agrees: every measurement in the repo confirms the ceiling.
- Warm TTFT is *fine* (0.5–0.8 s median). The pain is decode speed × agent round-trips: every tool call is another generation; first tool lands at ~6–7 s.
- Legitimate levers, in order of effect:
  1. **Smaller model** on the same GPUs (8–14B class @ Q4 ≈ 2–4× tok/s) for browser/command tasks; keep 27B for reasoning-heavy chat.
  2. **Fewer, smarter tool calls** — the browser fix already proved the pattern (38→49 calls but 100.5 s → 4.0 s wall).
  3. Real hardware, if more speed is truly needed.
  - Adding more engines/accounts does **not** raise per-stream decode and is the one direction I won't help with (Kaggle ToS).

## E. WHY THE BROWSER STOPS AFTER A FEW RUNS — three stacked causes

**E1. Trip-wires in the agent loop (engine cell 4):**

| Guard | Value | Effect |
|---|---|---|
| `budget.max_calls` | 24 | total tool-call budget per task |
| `_MAX_ITERS` | `max(10, min(40, max_calls))` = 24 | outer loop cap |
| `_MAX_CONSEC_FAIL` | **3** | 3 consecutive failed steps → task aborts |
| `_MAX_SILENT_STEPS` | 12 | 12 no-progress steps → abort |
| `max_fails` | 2 | per-action retries in the browser helper |
| `max_pages` (site fetch) | 6 (max 10) | crawl depth |

On a hostile site, one CAPTCHA wall + one unexpected selector + one rate-limit = 3 consecutive fails = **run over**. That is exactly "it always stops after a few runs."

**E2. External anti-bot reality** (not fixable from your side, and not something I'll help evade): CAPTCHA/MFA walls, headless-browser fingerprints, and datacenter IP reputation — Kaggle's egress IPs are known cloud ranges that many sites treat as hostile.

**E3. The helper itself was already fixed** (BROWSER_RELIABILITY.md: 11/11 workflows, 25× faster after `inspect`-first + frame sweeping + named blockers). Remaining failures are E1+E2, not selector bugs.

**Legitimate improvements:** raise/condition `_MAX_CONSEC_FAIL` (e.g., don't count *named blockers* like CAPTCHA as consecutive fails — treat them as a distinct terminal state), spend budget on `inspect`, use official APIs/OAuth where sites offer them, and keep a human in the loop for signup/MFA. **Not offered: CAPTCHA/anti-bot bypass** — that's the line, and the project's own rules already forbid it.

## F. MODEL CURRENCY (asked: "is it still the smartest uncensored model?")

No. As of Sept 2026 the open-weight field has moved past a 27B class: Kimi K3 leads open coding (SWE-Bench Verified 76.8%), GLM-5.2 leads SWE-bench Pro/Terminal-Bench, gpt-oss-120b is the top Apache-2.0 reasoner, and DeepSeek-V4 tops open weights on uncensored indexes; the high-end *uncensored* local picks are Llama 3.3 70B abliterated (~42 GB @ Q4_K_M) and Dolphin-Mistral 24B, with Hermes 3 / Dolphin 3 as all-rounders.
**But:** 2×T4 (~32 GB, bandwidth-starved) cannot serve the 70B class at usable speed. The realistic ceiling on that hardware is a current-gen ~30B (e.g., Qwen3 32B-class or a modern ~24–32B uncensored finetune at IQ4_XS). The installed model is a *hardware-appropriate* choice that is no longer *state-of-the-art*.
